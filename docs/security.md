# セキュリティ・プライバシー方針

## 1. 秘密情報管理
- Supabase **Service Role Key** はクライアント（Expoアプリ）に一切含めない。`.env` に置く場合もサーバー/Edge Function専用の変数名（`SUPABASE_SERVICE_ROLE_KEY`、`EXPO_PUBLIC_` プレフィックスを付けない）で管理し、`.gitignore` 対象とする。
- **AI APIキー**（STT/LLM/TTS）も同様にクライアントへ渡さない。`AI_API_KEY` はサーバーサイド（Edge Function実行環境）専用とし、Phase1時点ではモックアダプタのみを使い、実キー未設定でも主要フローが動くことを既定にする。
- クライアントに置いてよいのは `EXPO_PUBLIC_SUPABASE_URL` と `EXPO_PUBLIC_SUPABASE_ANON_KEY`（匿名キー）のみ。匿名キーは公開前提のキーであり、権限はRLSで担保する。
- `.env.example` に必要な変数名とコメントのみを記載し、実値はコミットしない。

## 2. 認可・RLS
- 全テーブルでRLSを有効化し、「本人のみ」「マッチ相手のみ」「ブロックされていない」等の条件をポリシーとして実装する（詳細: docs/data-model.md、実装: supabase/migrations）。
- クライアントは常にログインユーザーのJWTコンテキストでSupabaseにアクセスし、`profile_id` 等をクライアントから信頼せず、`auth.uid()` をポリシー側で強制する。
- 管理者操作（モデレーション、削除承認等）はPhase4で専用ロール（`app_role = 'admin'` をJWT claimまたは別テーブルで判定）を導入し、一般ユーザーとは別ポリシーで制御する。
- RLSの実効性は「他人の非公開データを取得できないこと」をテストで確認する（Phase2以降、supabase local + pgTAP相当またはJSクライアントでの権限テストを追加予定。Phase1では設計とポリシー適用まで）。

## 3. 位置情報
- 正確な緯度経度・現在地は取得も保存もしない。
- ユーザーは「大まかな活動エリア」（市区町村レベルの文字列）と「移動可能距離の目安（km）」のみを入力する。
- デート提案・チャット等でも、自宅・勤務先・正確な位置・非公開の予定を相手やAI説明文に表示しない（Phase3のAI出力検証で強制）。

## 4. 音声データ
- 録音は明示的な同意画面の表示・マイク使用中インジケータの常時表示を前提とする（`voice-onboarding` 画面で実装）。
- 生音声は**既定で文字起こし完了後に削除**する。音声プロフィール・音声メッセージとして本人が「保存する」を選んだ場合のみ、`voice_assets.retain_until` に期限を設定して保持する。
- 音声・文字起こし・AIメモリ（`ai_preference_facts`）はそれぞれ個別に閲覧・削除できるUI導線を用意する（Phase1: 設計とスキーマ、Phase2以降: 削除UI実装）。
- 音声・文字起こしへのアクセスはRLS + Supabase Storageの署名付きURL（期限付き）で保護する。

## 5. プロフィール・AIの推測禁止事項
- 年齢・性別等は本人が明示入力した値のみを使用する。
- 写真・声・返信速度・訛り等から、性格・人種・健康状態・宗教・性的指向・経済状態を推測しない。これはUI/AIプロンプト双方でのハード制約とし、`docs/PRD.md` 非スコープにも明記した。
- 推薦理由（`match_score_cache.reasons`）は、本人が明示的に入力・選択した情報のみを根拠として生成する。

## 6. ブロック・通報
- ブロックすると、双方の推薦・プロフィール閲覧・チャットから即時非表示にする（RLSのブロック判定関数を全ての可視性クエリに適用）。
- 通報は `reports` テーブルに記録し、モデレーションキュー（Phase4）で管理者が確認できるようにする。

## 7. アカウント削除
- 自分のデータ閲覧・退会・削除申請の導線をPhase1以降で段階的に実装する（Phase1: プロフィール閲覧・ログアウトまで。削除申請フローはPhase4で管理・監査ログと合わせて実装）。
- 削除方針: 削除申請後、猶予期間を設けたうえで個人を特定できるデータ（プロフィール本文、写真、メッセージ本文、音声・文字起こし）を削除し、統計目的の匿名化された集計データのみ保持する方針を採用する（詳細ポリシーはPhase4で確定）。

## 8. 入力検証・レート制限・モデレーション
- 全フォーム入力はZodスキーマでクライアント側検証を行い、AIから抽出された構造化データも同一スキーマで検証する（不正・不完全な場合は安全なフォールバックに倒す）。
- レート制限・画像/テキストモデレーションは、Phase1時点ではインターフェース（`src/lib/moderation` のスタブ）のみ用意し、実プロバイダ接続はPhase2以降で行う。
- SQLインジェクション対策としてSupabase Client（パラメータバインディング）以外の生SQL文字列結合は行わない。

## 9. プロンプトインジェクション対策（Phase2以降のAI機能向け設計方針）
- ユーザー発話・入力は常に「信頼できないデータ」としてLLMへ渡し、システムプロンプトとユーザー入力を明確に分離する。
- LLM出力はZod/JSON Schemaで検証し、スキーマ逸脱時は安全なテンプレート応答にフォールバックする。
- 「自動送信の禁止」「本人確認を必須にする」等の重要制約は、LLM任せにせずアプリケーションロジック側でも強制する（LLMの指示追従に安全性を委ねない）。

## 10. ログ・監査
- パスワード、メッセージ本文、個人情報（生年月日、連絡先等）をログに出力しない。
- Phase4で管理者操作の監査ログ（`moderation_actions` 等）を実装する。
