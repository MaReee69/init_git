# セキュリティ・プライバシー方針

## 1. 秘密情報管理
- Supabase **Service Role Key** はクライアント（Expoアプリ）に一切含めない。`.env` に置く場合もサーバー/Edge Function専用の変数名（`SUPABASE_SERVICE_ROLE_KEY`、`EXPO_PUBLIC_` プレフィックスを付けない）で管理し、`.gitignore` 対象とする。
- **AI APIキー**（STT/LLM/TTS）も同様にクライアントへ渡さない。`AI_API_KEY` はサーバーサイド（Edge Function実行環境）専用とし、Phase1時点ではモックアダプタのみを使い、実キー未設定でも主要フローが動くことを既定にする。
- クライアントに置いてよいのは `EXPO_PUBLIC_SUPABASE_URL` と `EXPO_PUBLIC_SUPABASE_ANON_KEY`（匿名キー）のみ。匿名キーは公開前提のキーであり、権限はRLSで担保する。
- `.env.example` に必要な変数名とコメントのみを記載し、実値はコミットしない。

## 2. 認可・RLS
- 全テーブルでRLSを有効化し、「本人のみ」「マッチ相手のみ」「ブロックされていない」等の条件をポリシーとして実装する（詳細: docs/data-model.md、実装: supabase/migrations）。
- クライアントは常にログインユーザーのJWTコンテキストでSupabaseにアクセスし、`profile_id` 等をクライアントから信頼せず、`auth.uid()` をポリシー側で強制する。
- 管理者操作（モデレーション、削除承認等）はPhase4で専用ロール（`app_role = 'admin'` をJWT claimまたは別テーブルで判定）を導入し、一般ユーザーとは別ポリシーで制御する。
- RLSの実効性は「他人の非公開データを取得できないこと」をテストで確認する（Phase2以降、supabase local + pgTAP相当またはJSクライアントでの権限テストを追加予定。Phase1では設計とポリシー適用まで）。

## 3. 位置情報
- 正確な緯度経度・現在地は取得も保存もしない。
- ユーザーは「大まかな活動エリア」（市区町村レベルの文字列）と「移動可能距離の目安（km）」のみを入力する。
- デート提案・チャット等でも、自宅・勤務先・正確な位置・非公開の予定を相手やAI説明文に表示しない（Phase3のAI出力検証で強制）。

## 4. 音声データ
- 録音は明示的な同意画面の表示・マイク使用中インジケータの常時表示を前提とする（`voice-onboarding` 画面で実装）。
- 生音声は**既定で文字起こし完了後に削除**する。「自分の言葉モード」「AI文案モード」の録音は文字起こし後に端末上のファイルを即時削除する（`deleteLocalRecording`、Phase3実装）。音声プロフィール・音声メッセージ（声のまま送る）として本人が明示的に送信を選んだ場合のみ、`voice_assets.retain_until` に期限（既定90日、`computeVoiceRetentionExpiry`）を設定して保持する。期限切れレコードを判定する純粋関数（`isVoiceAssetExpired`/`selectExpiredVoiceAssets`）はPhase3で実装・テスト済みだが、定期実行ジョブ（cron/Edge Function）自体はPhase4以降。
- 音声・文字起こし・AIメモリ（`ai_preference_facts`）はそれぞれ個別に閲覧・削除できるUI導線を用意する（Phase4で実装予定）。
- 音声・文字起こしへのアクセスはRLS + Supabase Storageの署名付きURL（期限付き）で保護する。

## 5. プロフィール・AIの推測禁止事項
- 年齢・性別等は本人が明示入力した値のみを使用する。
- 写真・声・返信速度・訛り等から、性格・人種・健康状態・宗教・性的指向・経済状態を推測しない。これはUI/AIプロンプト双方でのハード制約とし、`docs/PRD.md` 非スコープにも明記した。
- 推薦理由（`match_score_cache.reasons`）は、本人が明示的に入力・選択した情報のみを根拠として生成する。

## 6. ブロック・通報
- ブロックすると、双方の推薦・プロフィール閲覧から即時非表示にする（RLSのブロック判定関数を全ての可視性クエリに適用）。マッチ済みの場合は`block_profile()` RPC（Phase3実装）が既存マッチを`unmatched`へ即時更新し、以後は`is_active_match_participant()`によりチャット（`messages`）にも一切アクセスできなくなる。RLSテスト・Playwright E2Eの両方で確認済み。
- 通報は `reports` テーブルに記録し、チャット画面から理由選択・詳細入力の上で送信できる（Phase3実装）。モデレーションキューでの管理者対応はPhase4。

## 7. アカウント削除
- 自分のデータ閲覧・退会・削除申請の導線をPhase1以降で段階的に実装する（Phase1: プロフィール閲覧・ログアウトまで。削除申請フローはPhase4で管理・監査ログと合わせて実装）。
- 削除方針: 削除申請後、猶予期間を設けたうえで個人を特定できるデータ（プロフィール本文、写真、メッセージ本文、音声・文字起こし）を削除し、統計目的の匿名化された集計データのみ保持する方針を採用する（詳細ポリシーはPhase4で確定）。

## 8. 入力検証・レート制限・モデレーション
- 全フォーム入力はZodスキーマでクライアント側検証を行い、AIから抽出された構造化データも同一スキーマで検証する（不正・不完全な場合は安全なフォールバックに倒す）。
- レート制限・画像/テキストモデレーションは、Phase1時点ではインターフェース（`src/lib/moderation` のスタブ）のみ用意し、実プロバイダ接続はPhase2以降で行う。
- SQLインジェクション対策としてSupabase Client（パラメータバインディング）以外の生SQL文字列結合は行わない。

## 9. プロンプトインジェクション対策（Phase2以降のAI機能向け設計方針）
- ユーザー発話・入力は常に「信頼できないデータ」としてLLMへ渡し、システムプロンプトとユーザー入力を明確に分離する。
- LLM出力はZod/JSON Schemaで検証し、スキーマ逸脱時は安全なテンプレート応答にフォールバックする。
- 「自動送信の禁止」「本人確認を必須にする」等の重要制約は、LLM任せにせずアプリケーションロジック側でも強制する（LLMの指示追従に安全性を委ねない）。

## 10. ログ・監査
- パスワード、メッセージ本文、個人情報（生年月日、連絡先等）をログに出力しない。
- Phase4で管理者操作の監査ログ（`moderation_actions` 等）を実装する。

## 12. Phase2: RLSの自動検証（実施済み）

実Supabaseプロジェクトが無い環境でも、ローカルのPostgreSQLに `auth.uid()`/`auth.role()` をSupabaseのGoTrueと同一仕様でスタブ実装し、実際のRow Level Securityを検証できるようにした（`supabase/tests/_local_test_setup.sql`, `supabase/tests/rls_test.sql`, `scripts/run-rls-tests.sh`）。

検証項目（2026-09-05時点で19件全てPASS）:
- マッチ前は他人のprofilesを直接SELECTできない／UPDATEしても実際には反映されない
- `get_candidate_pool()`（候補抽出RPC）が年齢・性別・距離のハード条件を正しく適用する
- ブロックすると双方向に候補・可視性から除外される
- 受信したいいね（likes）は相互マッチ前は非公開
- `matches`テーブルへの直接INSERTは拒否され、`finalize_match()`（相互いいね確認RPC）経由でのみマッチが作成される
- `recommendation_events`は本人分のみINSERTでき、他人になりすませない
- `moderation_actions`は一般ユーザーから常に不可視（ポリシー未定義=デフォルト拒否）
- 未認証(anon)は`profiles`を一切参照できない

実装したRLSポリシー自体は全項目で意図通りに機能した（テスト作成時に発覚したのは、テスト側の前提の誤り2件——(1) RLSでUPDATE対象外の行は0件更新になるだけでエラーにはならないため「エラーになること」を期待するのは誤り、(2) 未認証状態のJWTクレームを空文字列に設定するとJSON解析エラーになるため、auth.uid()/auth.role()のスタブ実装側でnullif等による防御が必要——であり、いずれもテストコード側を修正した。候補抽出とマッチ成立はSECURITY DEFINER関数（RPC）に閉じ込め、`matches`テーブルへの直接INSERT権限をクライアントへ与えない設計とした。

## 13. Phase3: チャット・デート機能のセキュリティ検証（実施済み）

Phase3で追加したRPC・RLSポリシーを、Phase2と同じローカルPostgreSQLテスト基盤で検証した（`supabase/tests/rls_test.sql` セクション8〜12、`scripts/run-rls-tests.sh`）。

検証項目（2026-09-07時点、Phase2分と合わせて38件全てPASS）:
- `messages`はactiveなマッチの当事者のみSELECT/INSERT/UPDATEできる（`is_active_match_participant()`関数を新設）
- マッチ当事者でないユーザーはメッセージの参照・送信のいずれもできない
- 個人の`date_feedback`（また会いたいか等の回答）はマッチ相手であっても直接SELECTできない
- `check_mutual_reunion_interest()`は真偽値のみを返し、片方だけの再会意思を相手に開示しない
- 双方の再会意思確認が取れるまで`create_second_date_proposals()`は拒否される
- `cast_date_proposal_vote()`は当事者以外を拒否し、双方が同じ案に「行きたい」と投票した時点で`date_proposals.status`を自動的に`confirmed`へ更新する
- 送信済み音声メッセージの`voice_assets`は、送信先のactiveなマッチ当事者のみ参照でき、非当事者は参照できない
- `block_profile()`は既存のactiveなマッチを即座に`unmatched`へ更新し、以後は当事者自身を含めて`messages`が一切参照・送信できなくなる（「ブロック時は即時非表示にする」要件をRLSレベルで担保）

また、Playwrightによる実ブラウザE2Eで以下を確認した（コンソールエラー0件）:
- 2アカウントでチャットを開き、テキストメッセージの送受信、音声モード選択時のマイク権限拒否時のフォールバック表示、通報/ブロックメニューの表示
- 双方がデート後アンケートに回答するまで「セカンドデート提案」画面が利用不可であること、双方回答後にAIが3案を生成し、双方が同じ案に投票すると自動確定すること
- ブロック実行後、双方のマッチ一覧から相手が消え、ブロック前のチャットURLへ直接アクセスしても「見つかりませんでした」と表示されること（RLSの検証結果と一致）
